# Credits

The Credits page uses the shared floating client navigation/profile and white title/action card on
the plain page background, with the balance/report tabs and Export CSV inside that header card, the
same placement Briefings uses for its own filters. Activity and credit requests render as one-line
rows in bordered list cards, matching the Briefings and Reviews row style; clicking an activity row
opens the credit details dialog, and an agency's pending request keeps its Review button inline. The
layout follows the same desktop/mobile gutters as other client sections, with each row dropping to
two lines on phones, without changing billing or export behavior.

This feature displays a client's monthly credits (see the [monthly credits design](../../../../docs/superpowers/specs/2026-09-27-monthly-credits-design.md)), the immutable ledger and additional-credit requests. A credit month is the first day of a UTC month (`YYYY-MM-01`); credits left in a month expire when it ends. Agency and client sessions read only backend-authorized records; designers have no credit interface.

The page opens on the current month. A month switcher (previous/next buttons and a select reaching 11 months back and 11 ahead, plus "All months") drives both the month card and the ledger. The card shows the month's available credits (`.credit-balance`), what it used and received (plan allowance, extras, net transfers), "N credits expire on <date>" while an open month still holds credits, or what expired for an ended month, and the plan in force. For the agency, the month bar offers **Set plan** always and **Add extra** and **Transfer** only for a month it can write to (the current month and the next 11); the client sees only its own figures.

- `credit-data.ts` is the feature's only Supabase access point. It reads the account, requests and the ledger in bounded pages, avoiding the default query row limit when exporting a longer history, via `useCreditAccount`, `useCreditRequests` and `useCreditLedger(clientId, month?)` (with a month, only that credit month's entries). `useCreditMonthSummary(clientId, month)` calls `credit_month_summary` (a projected allowance for an untouched month), and `useCreditPlans` reads the plans' amount and start month. Both are keyed under `credit-account`, so every write that refreshes the balance, including accepting a briefing, refreshes them too; switching months keeps the previous figures on screen until the next arrive. The write functions — `requestCredits`, `adjustCredits`, `reviewCreditRequest`, `setCreditPlan`, `addMonthExtra`, `transferMonthCredits` — are plain `async (database, input)` functions unit-tested in `credit-data.test.ts` without React. The monthly ones keep the error code, so a month outside the writable range (errcode 22023) reads "Choose the current month or one of the next 11 months." and a short month states its available credits and shortfall (`describeCreditError` in `credit-model.ts`). `creditQueryKeys` and `useInvalidateCredits()` handle post-mutation cache invalidation.
- `credit-model.ts` holds the month math (`creditMonthOf`, `addCreditMonths`, `creditMonthRange`, `writableCreditMonths`, `daysLeftInMonth`), `planForMonth`, `expiringNotice` (only in a month's last 7 days) and the ledger kinds and labels. It filters ledger activity by credit month (the month an entry counts against, not the day it was written), campaign, project, type and search. It builds a CSV with a Month column (`YYYY-MM`), the reference report columns, the deliverable breakdown and a Note: the scope note for a project debit, the recorded reason for anything else. User text is quoted and formula-like cells are neutralized; numeric negative debits remain numbers. `formatCredits(count)` is the one place a credit count becomes words — the grouped number and its unit, singular only for exactly one — shared by the account menu's Credits block, the project chip below and the client Overview's per-project credit line (`features/overview/client-overview-page.tsx`), instead of each declaring its own `Intl.NumberFormat` and singular/plural ternary.
- `credits-page.tsx` renders balance/activity and a client report, scoped filters, downloadable CSV, details and request status. A `?project=` deep link opens the relevant project report.
- `credit-actions.tsx` creates 25/50/100 credit requests, reviews fulfillment/decline, and records agency adjustments by calling `requestCredits`/`adjustCredits`/`reviewCreditRequest` from `credit-data.ts`; it holds no direct Supabase call. It keeps the amount parsing/validation, the package check, note trimming, and the adjustment idempotency key (an `attempt` ref plus `crypto.randomUUID()`) reused for retries of the same payload; changing the payload creates a new key. Fulfillment relies on the backend's idempotent transaction. `CreditMonthDialog` is the agency's Set plan / Add extra / Transfer form, offering only the current month and the next 11; it validates whole numbers, requires a reason the client sees for an extra or a transfer, refuses a transfer within one month, and keeps one idempotency key per payload in the same way (`credit-actions.test.tsx`).
- `credit-meter.tsx` supplies the credits part of the header's account menu (`features/workspace/account-menu.tsx`), not this feature's own page. `useCreditMeter(clientId, viewer)` reads the current UTC month's `useCreditMonthSummary()` into the month's available credits, a 0–1 `ratio` of what the month received (allowance, extras and net transfers) still left, an `attention` flag for a balance at or below zero, and `expiring` — the amount and day — during the month's last 7 days. It returns null for a designer, a null viewer, a loading month or an error, never a stale or placeholder amount; the ratio is null when the month received nothing, and then the menu shows the number without a ring or dot bar. `CreditRing` draws the share left around the avatar, with its track in the attention tone when credits are about to expire (the trigger's label then adds "N credits expiring this month"); `CreditMeterPanel` shows "N left" linking to `/clients/:id/credits`, a 24-dot bar for the same share, "N credits expire on <date>" when relevant, and one role action — **Request credits** for a client, **Adjust credits** for the agency — which the menu opens as the existing `CreditActionDialog`. Its styles live in `credit-meter.css`, imported by the component, because `credits.css` only loads on the Credits route.

- `project-credits-chip.tsx` shows the credits a project used in the right corner of its title card (`features/projects/project-header.tsx`), so a client knows what the project is worth. It is information only, not a link, and reads `useProjectCreditUse(projectId)`: the project's `project_debit`, `project_refund` and `final_adjustment` ledger rows, summed as a positive number by `projectCreditsUsed` in `credit-model.ts` (a debit written when its budget is accepted, a refund and a new debit when it moves to another month, and its final settlement). The query key starts with `credit-ledger`, so every existing ledger invalidation refreshes it. It renders nothing for a designer, a null viewer, a loading or failed read, or a project without a debit, and the hook waits for the profile so a designer's page never sends the request. Its base look is `credit-chip.css`; on phones the word "credits" is visually hidden but still read.

Routes live under `app/(workspace)/clients/[clientId]/credits/`; feature styles are in `credits.css`. Shared dialogs use Modal. Mutations call `useInvalidateCredits()` after success, which invalidates the account/ledger/request/notification queries. Errors are shown without changing local balances or claiming an allocation succeeded.

See [the data-access contract](../../../../docs/architecture/data-access.md) for the rules this feature's `credit-data.ts` / `credit-actions.tsx` split follows, cited there as the worked example for every other feature.

A client request does not grant credits or collect payment. Agency allocation is an explicit accounting action with a reason. There is no payment gateway or fabricated payment confirmation. Negative adjustments represent corrections and are still subject to backend balance and authorization checks.

Verification from `apps/web`:

```sh
npm run test -- features/credits features/workspace/account-menu.test.tsx
npm run test:e2e -- tests/e2e/intake-admin.spec.ts tests/e2e/project-credits.spec.ts
npm run typecheck
./node_modules/.bin/eslint features/credits 'app/(workspace)/clients/[clientId]/credits'
```

Focused tests cover UTC month math, plan resolution, the expiry window, error wording, combined filters by credit month, signed activity, CSV scope/columns/escaping and formula injection, the month forms and their idempotency keys, and the account menu's expiry signal. Account reconciliation, role isolation, concurrent acceptance/adjustment and authenticated request fulfillment require the separate database/browser evidence tracked in the [acceptance matrix](../../../../docs/architecture/acceptance-matrix.md).
