## Spike findings (2026-09-26)

Restated from [the design's spike](../superpowers/specs/2026-09-26-miro-mode-design.md#objective)
(lines ~15-23), as evidence recorded there from the 2026-09-26 spike against the user's own board —
not re-run in this session:

- The live embed loads without a Miro login in Chromium and WebKit.
- On a board shared as "anyone with the link can edit", the embed opens in Editing mode.
- Without `autoplay=true` the embed shows a "See the board" preview that needs an extra click —
  the reason `miro-links.ts`'s `miroEmbedUrl` always sets `autoplay=true`.
- Copying an image on the product's page and pasting it inside the embed (Cmd/Ctrl+V) creates the
  image on the board. Verified by automation and by the user.
- Dragging an image from the product's page into the embed does **not** work (tested by the user);
  drag is out of scope, which is why the Playground's asset strip in Miro mode only offers **Copy**,
  never drag-to-board.

## Delivered behavior verified

- A client enters Miro mode from the header's **Project view** group (**Miro**) and sees the newest
  linked version, autoplaying (`live-embed/uXjVClientE2E%3D/?autoplay=true&moveToWidget=111`); the
  internal board never mounts; the URL carries `view=miro`.
- The project's other tools stay reachable beside the frame: **Conversation** opens `.project-inspector`
  without unmounting `iframe.miro-view-frame`; the **Playground** icon toggles the asset strip
  (`PlaygroundAssetStrip`), whose **Open full Playground** button is present.
- A reload keeps Miro mode (URL-persisted state); switching back to **Versions** unmounts the frame
  and drops `view=miro` from the URL; entering again from a version card's **View on Miro** works.
- An assigned designer visiting `?view=miro` sees only the internal board; a stale `version` query
  value falls back to the newest linked one for the client.

## Copy check (spike finding)

The seeded SABRE client's Brand Hub has no folders, so all 15 assets land in one **Unfiled** album;
it is copyable — the first file alphabetically, "Campus Connections - Campaign photography", is
`image/png`. The spec opens that album, clicks **Copy Campus Connections - Campaign photography**
(clipboard permissions granted via `context.grantPermissions`), and asserts the status text
`Copied — paste in Miro with ⌘V / Ctrl+V`. Copy failure/download-fallback paths remain covered by

## Visual check (Step 3)

Screenshots in the git-ignored `outputs/miro-mode/`: `strip-1440-light.png`, `strip-1440-dark.png`,
`strip-390-light.png`, `strip-390-dark.png` (asset strip open), `conversation-1440-light.png`,
`conversation-1440-dark.png`, `conversation-390-light.png`, `conversation-390-dark.png`
(Conversation open). None are committed — no captured image needed a permanent citation beyond this
record's description, and the embed itself renders blank in this environment (no real Miro
session/board), same limitation as the prior Task 7 record.

Observations:

- **Tool bar vs. Miro's zoom controls:** at 1440 px the tool bar sits centered at the canvas bottom,
  clear of Miro's own bottom-left zoom pill. At 390 px with a side panel open, `projects.css`
  deliberately hides the tool bar below an 800 px container width
  (`@container board (max-width: 799px) { .project-workspace:has(> .project-inspector)
.project-tool-bar { display: none; } }`) rather than overlapping it — by design, not a gap found
  here.
- **Selector/Open in Miro at 390 px:** both fit on one row with no wrap or clipping in every
  capture.
- **Strip overflow:** `.playground-album-chips` has `overflow-x: auto`; the chip row scrolls inside
  the strip rather than overflowing the page at 390 px.
- **Focus order:** starting from the already-focused Playground toolbar button (opening the strip),
  Tab reaches, in order: the "Miro frame" selector, **Open in Miro**, then the strip's album chips
  and **Open full Playground** — i.e. tool bar → selector → Open in Miro → strip, matching the
  required order (the tool bar is the starting point here since it was just clicked to open the
  strip).
- **Dark theme:** both layouts re-theme correctly (background, border, muted/foreground text) with
  no unstyled element.
